# 틀린시연찾기 — 자기개선 루프 운영서 (LOOP)

매일 아침 자동 실행되는 개선 루프의 절차입니다. **루프는 이 문서를 스스로 고쳐 가며 발전합니다**(맨 아래 "루프 자체 개선").
단, 예약 작업 지시문에 적힌 **고정 원칙**은 이 문서로 바꿀 수 없습니다.

목적: ① 쌓인 의견·오답을 매일 읽고 ② 사람 개입 없이 고쳐 배포하고 ③ 배운 것을 규칙(`src/LESSONS.md`)으로 남겨 같은 실수를 다시 만들지 않는다 ④ 고친 결과를 다음 날 데이터로 검증하고, 나빠졌으면 스스로 되돌린다.

## 매일 하는 일
(날짜는 **KST** 기준. 예약 실행은 KST 아침 = UTC 전날 밤이므로 리포트 파일명·장부 날짜는 `TZ=Asia/Seoul date`로 정한다.)
0. 저장소 클론 → `src/LOOP.md`(이 문서) · `src/LESSONS.md` · `src/CHANGES.md` 읽기.
1. 시트와 취합표 「의견 취합」 탭 읽기. 팀장이 취합표에 직접 적은 행(처리 상태 비었거나 「접수」)도 의견으로 취급.
2. **어제까지의 변경 검증**: CHANGES.md에서 상태가 `검증 중`인 항목마다, 변경 뒤 쌓인 기록으로 지표를 비교한다(해당 스텝 오답률, 해당 스테이지 완주율·👎 비율).
   - 변경 뒤 기록 3건 이상에서 나아졌거나 같으면 → `확정`.
   - 3건 이상에서 뚜렷이 나빠졌으면(오답률 +20%p 이상, 또는 그 변경을 지목한 부정 의견) → **자동으로 되돌린다**(해당 커밋 git revert → 빌드 → 전 스테이지 자동 플레이 → 배포) → `되돌림` + 사유. 관련 규칙이 있으면 LESSONS.md의 적용 방법을 고쳐 쓴다.
   - 기록이 3건 미만이면 그대로 둔다. 14일이 지나도 3건 미만이면 `확정(데이터 부족)`.
3. 신규 데이터 요약: 참여 인원·건수, 모드·사무소·스테이지별 평균, 의견 kind별 건수(👍/👎 비율).
4. 문제 지점 분석: 스텝별 오답률·시간·시간초과, 오클릭 좌표를 보드 이미지에 찍어 무엇을 눌렀는지 확인 → 원인. why 신고가 있으면 사용자가 고른 이유를 우선. 원장님 질문·사이트 퀴즈 오답 TOP. 새 의견 원문 전부 인용.
5. **자동 반영(사람 승인 없이)** — 아래는 근거가 있으면 바로 고친다.
   - 문구·힌트·찬스: 서로 다른 2명 이상이 같은 지점을 눌러 틀림 / why 「문제가 모호」 2명 이상 / 명시적 의견 1건이 화면으로 확인됨.
   - 정답 영역(rect): 정답 이의·의견·why 「정답 위치가 이상」이 보드에서 확인됨(1명이라도 오클릭 좌표가 정답으로 볼 만한 곳을 정확히 가리키면 포함).
   - 화면 구성·사용성(UI): 글자 크기, 위치, 순서, 가림, 버튼 크기, 안내 문구 길이, 색 대비처럼 **보기·누르기 편하게 하는 변경**. 명시적 의견 1건 이상이 있고 LESSONS.md 규칙과 충돌하지 않을 때. 한 번에 한 가지 변경만(무엇이 효과였는지 가리기 위해).
   - 난이도·흐름: 한 스테이지의 완주율이 서로 다른 3명 이상에서 40% 미만이면 힌트를 보강하거나 스텝 설명을 나눈다(스텝 삭제는 하지 않음).
   - 오탈자, 깨진 표시, 오류.
   - 같은 패턴 전수 점검: 오늘 고친 문제·새 규칙과 같은 패턴의 다른 스텝을 전체에서 찾아 한 번에 최대 5스텝까지 함께 고친다. 신규 데이터가 없는 날에는 LESSONS.md에서 아직 `점검:` 표시가 없는 규칙을 하루에 하나씩 전수 점검한다. 5스텝 한도로 못 고친 위반은 그 규칙의 점검 메모에 `미룸: 스텝id(이유)`로 남기고, 다음 실행은 새 규칙 점검보다 `미룸:`을 먼저 처리한 뒤 메모에서 지운다.
6. **자동 반영하지 않는 것(취합표에 「팀장 판단 필요」로, 권고안 1개와 근거 숫자를 함께)**: 고정 원칙에 해당하는 것, 스테이지·코스 추가/삭제, 새 화면 캡처가 필요한 보드 교체, 점수·등급·자격 기준 변경.
7. 반영 절차: `src/` 수정 → 빌드(lint 오류 0) → **전 스테이지** Playwright 자동 플레이 클리어 확인(`node src/game/autoplay.js` — 빌드된 루트 index.html 사본으로 19스테이지를 돌리고 외부 네트워크를 막아 시트에 기록을 남기지 않음. 끝줄 '전 스테이지 클리어'·exit 0이 통과. 오래 걸리면 백그라운드로 돌리고 로그를 본다)(UI 변경이면 PC·폰 세로 둘 다, 스크린샷으로 지시문 띠·보드·버튼이 가려지지 않았는지 확인) → `parts/changelog.html` 맨 위에 버전 한 줄(의견으로 고쳤으면 "의견 반영" 명시) → 커밋·push → CHANGES.md에 한 줄 추가(상태 `검증 중`, 기준 지표 기록). 하나라도 실패하면 배포하지 않고 변경을 버린 뒤 리포트에 남긴다.
8. 규칙 갱신: 다음에도 적용될 교훈이면 LESSONS.md 맨 아래에 추가(번호 · 규칙 · 근거 · 적용 방법). 2명 이상의 데이터나 명시적 의견이 근거일 때만. 겹치면 기존 규칙의 근거에 덧붙인다. 전수 점검을 마친 규칙에 `점검: YYYY-MM-DD, n건 수정`. 취합표 「학습된 규칙」 탭에도 같은 행 추가·수정.
9. 리포트 `reports/YYYY-MM-DD.md` 커밋: ① 오늘의 숫자 ② 어제까지 변경의 검증 결과(확정/되돌림) ③ 막힌 곳 TOP5 ④ 새 의견 원문 ⑤ 자동 반영한 것(전/후) ⑥ 오늘 배운 것 ⑦ 팀장 판단이 필요한 것(있을 때만, 최대 3개) ⑧ 의견 수집 상태(최근 7일 의견/훈련 비율. 10% 미만이면 수집 방식 자체를 5번 UI 변경 기준으로 개선).
10. 취합표 갱신: 「의견 취합」에 아직 없는 의견만 마지막 기록 아래에 추가(stage·idea·dispute·quit·why는 한 건당 한 행, tap은 숫자만). 처리 상태 = 반영 완료(+버전·내용) / 팀장 판단 필요 / 접수. 예전 「접수」 행을 고쳤으면 채운다. 기존 원문과 팀장이 바꾼 값은 덮어쓰지 않는다. 「복구 대상」은 그 사람 의견이 시트에 들어오면 시트 도착을 「도착」으로.
11. 마지막 메시지: 3~6줄 요약(참여·의견 건수, 검증 결과, 반영한 것, 배운 규칙, 팀장 판단이 필요한 것). 아무 변화도 할 일도 없으면 "신규 기록 없음" 한 줄.

## 조용한 날의 자기 점검 (신규 기록이 7일 이상 없을 때, 주 1회)
전 스테이지를 PC·폰 세로로 자동 플레이하며 스크린샷을 찍어 LESSONS.md 규칙 위반(지시문 가림, 저해상도 보드, 같은 라벨 중복, 힌트가 목표어 반복 등)을 찾는다. 5번 기준에 맞으면 고치고, 리포트에 "자기 점검"으로 남긴다.

## 루프 자체 개선
이 문서의 절차가 비효율적이거나 틀렸다고 판단되면(예: 검증 기준이 너무 느슨/엄격, 빠뜨린 점검, 반복되는 실패) 루프가 이 문서를 직접 고친다. 고칠 때는 맨 아래 변경 이력에 날짜·무엇을·왜를 한 줄 남긴다. 고정 원칙을 약하게 만드는 수정, 자동 반영 범위를 6번 항목까지 넓히는 수정은 하지 않고 리포트의 "팀장 판단 필요"로 올린다.
